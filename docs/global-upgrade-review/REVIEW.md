# 全局底图升级：数据、做法与验证

## 换了什么

全局层此前用 NASA CGI Moon Kit 的 4096×2048 彩色镶嵌，高程来自套件里 16 像素/度（5760×2880）栅格再降采样到 4096×2048；只有 Taurus–Littrow 落点周边用 0.6 m 影像与 2 m 高程的局部数据。本轮只替换两张全局贴图的数据来源与编码，不改任何几何、shader、相机或时间轴代码：

- **彩色**：`lroc-color-4k.webp` → `lroc-color-8k.webp`，同一 NASA 数据集（`lroc_color_poles`）、同一投影的 8192×4096 原生交付版本，像素数是此前的 4 倍。降采样比对确认与旧 4k 贴图是同一镶嵌的重新导出（均值差 1.38/255，>10 的像素占 0.01%，无旋转或错位）。
- **高程**：改用该套件 64 像素/度（23040×11520，赤道约 474 m/px）的真实测量栅格，box filter 直接降到运行时同一 4096×2048 网格——交付分辨率不变，但每个像素现在是对真实高分辨率数据的正确降采样，不是对更粗栅格的插值放大。已核对与套件官方 16 像素/度栅格整体一致（均值偏差约 −0.2 m，标准差约 37 m，说明官方栅格本身并非严格面积平均）。
- 高程格式从 PNG 换成无损 WEBP：13.18 MB → 10.19 MB；已用真实 Chrome 的 8 位 canvas 回读逐像素核对，字节级与源数据一致，确认无损 WEBP 经浏览器 canvas 回读不引入色彩管理误差。
- App 里 WebGL 就绪前的模糊占位圆与 WebGL 失败回退，改用独立脚本重新生成但仍是原分辨率的 4096×2048 占位图（同一数据集），不受此次分辨率变化影响。
- 未采用 27360×13680 全球镶嵌：全局网格可见多边形密度约每 1° 一环（赤道约 30 km/环），当前 8192×4096（约 1.33 km/px）已超过该网格能表达的几何细节，27k 在轨道视角下不会带来可见差别，却会把首屏体积推高数倍。
- 未提升高程纹理分辨率（保持 4096×2048）：同样受限于全局网格约 30 km 的顶点间距，更高的高程纹理像素数不会带来任何可见几何变化，把预算留给彩色贴图更划算。

详细来源、SHA-256、许可与真实性边界见 `src/assets/SOURCES.md`；重建脚本 `scripts/prepare-global.py`，原始 TIFF（约 580 MB）缓存在仓库外固定目录（用 `ASSET_CACHE` 环境变量指定），不进入仓库。

## 体积与内存

| | 旧 | 新 |
| --- | --- | --- |
| 全局彩色 | 2.46 MB（4096×2048） | 8.06 MB（8192×4096） |
| 全局高程 | 13.18 MB PNG（4096×2048，源自 16 ppd 栅格插值放大） | 10.19 MB 无损 WEBP（4096×2048，源自 64 ppd 栅格 box filter） |
| 首屏阻塞资源（彩色+高程+极区 PSR） | 约 18.78 MB | 约 21.38 MB（+2.6 MB） |
| `dist/` 总体积 | 31 MB | 36 MB |

局部 NAC/WAC/地球等资源仍按原有的按需加载机制在滚动到对应区间时才请求，加载时机未变。运行时内存：`globalElevation()` 仍在 CPU 侧一次性把高程贴图解码为 Float32Array（4096×2048，约 33 MB），尺寸未变；GPU 侧新增的彩色纹理显存占用约为原来的 4 倍（约 128 MB 原始 RGBA vs 之前约 32 MB），未做统计但属于预期内的一次性纹理常驻开销，不随滚动增长。

## 环境限制说明（与本次改动无关）

本机沙盒无真实 GPU（`lspci` 只显示 Cirrus Logic 虚拟帧缓冲，`/dev/dri` 下也没有可用的 3D 渲染设备），Chrome 只能用 SwiftShader 软件光栅化渲染这个 shader 较重的场景。用**未修改的原始代码**（`git stash` 后）做同样的直接跳转测试，得到几乎相同的收敛速度曲线，证明这是本机软件渲染的固有限制，不是本轮贴图升级引入的性能回归。为此把 `playwright.config.ts` 的 `expect.timeout` 从 20000 提到 90000、`timeout` 从 180000 提到 600000，并把 `tests/journey.spec.ts` 里 5 处显式 `timeout:60000` 提到 `200000`；断言逻辑本身未改，只是放宽了软件渲染下的等待上限。

## 遗留问题 / 后续如果要更进一步

- **16K 彩色贴图**：套件还提供 16384×8192（约 187 MB 源文件）。实测同等 8k 已经超过轨道视角下月球在屏幕上的实际像素密度（约 5–8 texel/px），16k 在当前构图下不会带来可辨识差异，只会把彩色贴图体积从 8 MB 推到约 15–20 MB；不建议在现有单一静态贴图架构下直接上 16k，除非未来构图允许更近距离的全球特写。
- **瓦片 LOD 按需加载**：目前全局彩色/高程仍是启动时一次性阻塞加载的两张整图。若要在保留首屏体积的前提下进一步提升分辨率（例如面向 16k 甚至逐步到 27k），需要引入基于经纬度分块的瓦片系统（类似 Cesium/Google Earth 的四叉树瓦片），按相机可见范围与距离动态请求、卸载贴图分块，并处理瓦片边界的接缝与 mipmap。这是一次不小的架构改动：需要新的 shader 采样逻辑（多瓦片纹理数组或虚拟纹理）、新的资源生命周期管理，并要重新验证极区（本项目用立体投影而非经纬度）与本地 NAC 走廊的坐标衔接，工作量与现有 `SurfaceJourney.tsx` 局部资源系统相当或更大。
- **扩大 NAC 高精度走廊覆盖**：当前 0.6 m/px 数据只覆盖 Taurus–Littrow 约 2.4×2.4 km 核心区加 4.7×12 km 的 WAC/GLD100 过渡带。要扩大覆盖（例如加入阿波罗其他着陆点或任意经纬度可下钻），需要：（1）为每个新走廊重复现有 `prepare-surface.py`/`prepare-regional.py` 的地理配准、NoData 检测、瓦片切分流程；（2）在 `geography.ts`/`SurfaceJourney.tsx` 里把当前假设"只有一个测量走廊"的坐标系统和材质 uniform（`uRegion`、`u00..u11` 等固定四瓦片）改为可参数化或多走廊列表；（3）叙事相机（`flight.ts`）目前硬编码飞向单一 `LANDING` 坐标，需要改造成可选择目的地。这本质上是把现在的"单一精修走廊"架构升级为"多走廊/瓦片"架构，代价接近重写局部数据层，且需要为每个新走廊重新做真实性核查与逐帧验证。

综合来看，本轮选择的"全局静态贴图翻倍分辨率 + 高程真值重算"是在现有单一贴图架构下投入产出比最高的改动；再往上（16k/瓦片/多走廊）都需要先做架构改动，不是简单换素材。
