# 全球 LOD 引擎方案：同一颗球、真实高程驱动、按相机视点分级

## 现状盘点（先弄清楚已经有什么，再决定补什么）

项目现在已经是一个**没有明说但确实存在的、以固定兴趣点为中心的分级网格系统**，理解这一点是本方案的出发点：

- `src/scene/geography.ts` 的 `planetGeometry()`：以 `LANDING`（Taurus–Littrow，固定经纬度）为中心，从外圈的全球 1° 经纬环（约 30 km/环）向内嵌套对分，直到 `minimum`（粗网格 768 m、精细网格 96 m）为止；每一圈的边缘顶点用"落在父网格边上"的方式消除 T 型接缝——这本质上就是一个**单点固定的 clipmap**，只是目前只服务于 Taurus–Littrow 这一个位置，而且是"建一次就不再变"，不随相机连续移动重建。
- 数据来源已经是三级真实数据：全球（本项目上一轮已升级为 8k 真实反照率 + 64 ppd 真实高程重算的法线贴图，无夸张）→ 区域（`prepare-regional.py`：Taurus–Littrow 周边 WAC 100 m / GLD100 100 m 真实数据）→ 局部（`prepare-surface.py`：0.6 m NAC 影像 + 2 m 高程）。
- 缺口很明确：**这三级数据只在 Taurus–Littrow 这一个坐标才存在**；相机稍微移开这个点，网格立刻退回全球 30 km 粗环 + 法线贴图（没有真实几何位移，只有着色补偿）。这正是本次任务要补的核心缺口。

## 目标架构

### 数据模型：等距柱状投影四叉树瓦片

不用立方体球（cube-sphere）或六边形网格，理由：项目现有全部数据管线（LOLA 64 ppd、CGI Moon Kit 彩色图、LROC WAC/GLD100、PSR 极区图层）全部原生是等距柱状投影（equirectangular），继续用同一投影可以直接复用现有 `geographic()/mapUV()` 坐标数学、现有资产、现有极区退化处理（`planetGeometry` 里 `|lat|>84°` 法线拉回径向的做法），不需要重新做投影转换。代价（等距柱状在极区网格畸变）用与现状相同的"高纬度混合到径向法线"策略处理，不追加新问题。

瓦片编号采用标准 `level/x/y`（等价于 WMTS/Slippy Map 规则）：

- `level 0`：整球 1 张瓦片（等价于当前的全球 8k 贴图 + 64 ppd 高程 + 法线贴图，已经是真实数据、已完成）。
- `level L`：把球面切成 `2^(L+1) × 2^L` 个经纬度矩形格（经度格数是纬度格数的两倍，保持格子接近正方形）。
- **限制型四叉树（restricted quadtree）**：任意两个相邻瓦片的层级差不得超过 1——这是让"不同 LOD 接缝"可控的关键约束，本项目现有 `planetGeometry` 的 `snap` 逻辑已经隐含遵守了这一条（每次只对分一层，且用边中点吸附解决 T 型缝），第二期把它推广到瓦片时继续遵守同一约束，复用同一手法，而不是发明新的裂缝修补算法。

### 瓦片内容（每张瓦片，三样东西，全部来自真实数据）

1. **高程网格**：小尺寸 Float32 网格（例如 65×65 或 129×129 顶点），来源按层级选择当前已有的真实数据源——`level 0-2` 用 64 ppd LOLA（本机已缓存 `ldem_64_uint.tif`，474 m/像素）；有 WAC/GLD100 覆盖的瓦片用 100 m 数据；有 NAC 覆盖的瓦片（目前只有 Taurus–Littrow）用 0.6 m/2 m 数据。**没有真实数据覆盖的瓦片，停留在上一级真实数据的双线性重采样，绝不用程序化噪声补"看起来像"的假细节**——这是硬约束，宁可分辨率低，不可以假。
2. **反照率贴图**：真实彩色影像，同样按层级选择 CGI Moon Kit 全球图 / WAC 100 m / NAC 0.6 m。
3. **法线贴图**：延用本项目上一轮已经验证过的方法（`scripts/prepare-global-relief.py`：对真实高程场做有限差分求法线，而不是对贴图做程序化凹凸），每一层级用该层级自己的真实高程数据重新计算，保证法线永远和这一层级实际展示的地形形状一致。

### LOD 选择：只吃相机位置，不吃滚动进度

选择函数签名设计为：

```ts
selectTile(cameraWorldPosition: Vector3, tile: TileBounds): 'keep' | 'split' | 'merge'
```

用标准的屏幕空间误差（screen-space error）或简化版"瓦片包围球到相机距离 / 瓦片实际地面尺寸"的比值阈值判定，**只依赖相机世界坐标，不依赖 `progress`/滚动时间轴**。现状 `src/scene/LunarScene.tsx` 里"是否加载 Taurus–Littrow 精细数据"的判断目前是 `progress>.18&&progress<.695`（滚动进度区间）——这是本方案明确要在第二期改掉的技术债：滚动驱动的电影运镜和相机世界坐标其实高度相关但不是一回事，只有换成"相机到兴趣点距离阈值"，未来自由相机（开车模式）才能复用同一套判断，不需要伪造一个"进度"。**本期（第一期）不改这一处**，原因见下方"为什么不做完整四叉树"。

### 裂缝处理

沿用项目已验证的两种手法，不引入第三种：

1. **共享边顶点吸附**（现有 `planetGeometry` 的 `snap` 参数逻辑）：相邻瓦片在层级差为 1 时，粗瓦片一侧的边缘顶点数量是细瓦片的一半，让细瓦片边缘的"奇数顶点"直接落在粗瓦片边上，杜绝 T 型缝——限制型四叉树保证了层级差永远不超过 1，这一手法就永远够用，不需要再实现裙边（skirt）之类的备用方案。
2. **同一弹性混合函数**（`fade`/`lerp`，`measuredElevation` 已经在用）：不同真实数据源交界处不是硬切换，而是在一条过渡带内线性淡入淡出，过渡带宽度和现有 `regionEdge`/`fineEdge` 用法一致。

### 加载预算与显存上限

- **常驻瓦片数上限**：以当前本地走廊系统实测的显存数字为基准（`docs/*/VALIDATION.md` 记录本地走廊贴图预算约数 MB 级），设计目标是"任意时刻常驻瓦片的贴图+高程总字节数不超过一个可配置上限（初始设定 64 MB，可调）"，超出时按"离相机最远的瓦片优先淘汰"（LRU + 距离加权）回收。
- **加载中的瓦片不阻塞渲染**：复用现有 `SurfaceJourney.tsx` 的模式——先用上一级（更粗）数据渲染，新瓦片在后台 `fetch`/解码完成后才替换，网络慢时相机像现在一样"停留在更粗但完整的画面"，不出现空洞。
- **同一深度缓冲、同一相机、同一网格体系**：不新增第二个场景、第二台相机或离屏 FBO；新增的瓦片网格都是同一个 `THREE.Group` 下的普通 mesh，和现有 `world.planet`/`planet` 共用材质工厂 `planetMaterial()`。

### 为"开放世界开车"预留的接口（现在就定义签名，具体实现留到后面）

1. `selectTile(cameraWorldPosition, tile)`：如上，只吃相机世界坐标——这样第三期换成自由相机时，这个函数不用改一行。
2. `PointOfInterest { center: Vector2 /* local x,z 米 */, radius: number, tiles: TileSource[] }`：把"Taurus–Littrow 是全网格里唯一的高精度点"这件事从硬编码的 `LANDING` 常量，改成一个可以有多条目的列表；第一期仍然只填一条（Taurus–Littrow），但读取路径不再假设"只有一个"。
3. `TileSource`：`{ level, x, y, elevationUrl, colorUrl, normalUrl, boundsWorld }`——瓦片描述用**运行时世界坐标（米）**而不是原始像素坐标，这样任何新增数据源（无论来自 4720 全球图、WAC 区域图，还是未来别的 NAC 走廊）接入时只需要提供同一个结构体，渲染代码不用关心它来自哪次下载。
4. 数据获取解耦：`TileSource.elevationUrl`/`colorUrl` 现在指向仓库内预处理好的静态资产；第三期如果要支持"开到任意经纬度都有区域级真实数据"，只需要把这两个 URL 换成指向一个运行时瓦片服务（可以是浏览器直接对接 LROC PDS 的 HTTP Range 读取，本项目 `prepare-regional.py`/`prepare-surface.py` 已经验证过这一整套技术在离线脚本里可行），渲染/LOD 选择/裂缝处理代码完全不用动。

## 分期

### 第一期（本次落地）

给"从轨道下降到 Taurus–Littrow"这段**现有真实存在的运镜路径**补一个真实几何 LOD 层，而不是新造一整套通用四叉树：

- 新增一份来自 64 ppd LOLA 原始栅格（`ldem_64_uint.tif`，本机已缓存，真实数据非新造）、以 Taurus–Littrow 为中心、边长约 128 km、原生 474 m/像素分辨率的高程小图（约 280×280 网格点，Float32 二进制约 300 KB）。
- 现有 `planetGeometry()` 在粗网格（`detail=false`，进入本地精细数据之前使用）已经把 Taurus–Littrow 周围的顶点密度做到 768 m 一环——但目前这些顶点采样的是全局 4096×2048（约 2.7 km/像素）高程贴图，比顶点密度本身还粗，等于"有骨架没肉"。接入这份新的 474 m 原生数据后，同一批顶点（网格拓扑、三角形数量完全不变）会显示出真实的、来源可信的小尺度地形起伏，而不是被 2.7 km 插值抹平的团块。**这是本期性价比最高的改动：零新增三角形、零新增材质分支、复用现成的边缘淡入淡出手法，只把"喂给已有骨架的肉"换成更细的真实数据。**
- 这份数据只在下降路径经过、且局部 NAC 数据尚未加载完成的这段过渡里可见（下降到 NAC 走廊数据加载完成后，精度更高的 NAC/区域数据接管，和现状行为完全一致）。
- 保留本项目上一轮已完成的全球法线贴图（真实高程驱动的全球光影）不变，作为 `level 0` 继续服务最远的轨道视角。
- 用小规模、有明确 `PointOfInterest` 概念雏形的数据结构组织新资产（一个 JSON 清单 + 一份二进制高程），为第二期改造成真正的列表打基础，但**不改动 `planetGeometry`/`LANDING` 现有的硬编码路径本身**——改数据源不改拓扑算法，风险最小。

### 第二期（设计已定，暂不实现）

- 把 `LANDING`/`REGIONAL` 从硬编码常量重构成 `PointOfInterest[]` 列表，`planetGeometry` 的嵌套环逻辑按"离相机最近的兴趣点"选中心，不再假设全局唯一。
- 把本地精细数据的加载触发条件从 `progress` 区间改成"相机到最近兴趣点的距离阈值"，同时保留 `progress` 只用于叙事文案/镜头本身（渲染判断和叙事解耦）。
- 引入真正的瓦片增删（不止一个兴趣点半径内固定网格，而是相机移动时动态创建/销毁瓦片 mesh），处理相机快速移动/掉帧下的加载竞态。

### 第三期（能力预留，暂不实现）

- 运行时（浏览器端）直接对接 LROC PDS 的 HTTP Range 瓦片读取，让"任意经纬度"都能取得至少区域级（约 100 m/像素）真实数据，不再局限于预处理好的固定走廊。
- 相机输入源从 `flight.ts` 的滚动插值换成自由输入（键盘/鼠标/手柄），`selectTile`/`PointOfInterest` 接口按方案设计已不需要改动。
- 评估在有真实高精度覆盖的地点（未来可能新增的 Apollo 着陆点等）之间做"驾驶"式地面漫游。

## 为什么不在本次直接实现完整四叉树

1. **回归风险**：现有 `planetGeometry` 的嵌套环 + 边缘吸附 + 极区退化是经过多轮验证、14 项自动化测试覆盖的代码，一次性换成通用多网格瓦片系统涉及场景图结构、材质工厂调用点、资源生命周期管理的大改动，在没有充分分阶段验证的情况下改动面过大。
2. **当前相机是脚本化运镜，不是自由相机**：现有下降路径永远飞向同一个 Taurus–Littrow 坐标，"相机随时可能出现在任意经纬度"这个场景目前并不会真的发生；先把通用四叉树的全部机制（动态增删、任意点瓦片竞态处理）做完，在没有自由相机验证的情况下无法真正测试到位，容易做出"看起来对但没被走到过"的代码。
3. **NASA 14959 精度考证结果**（见 `docs/model-14959-assessment.md`）确认：即便是 NASA 官方现成的"整月轨道级"模型，网格顶点间距也在 3–4 km 量级，仍然回答不了"任意点都能看清地表细节"的问题——这说明"任意经纬度都能开到贴地精度"目前受限于**全月范围内根本没有均匀覆盖的真实高精度数据**，不是工程实现问题；引擎架构可以提前设计好接口（已在上面写明），但没必要在数据本身不支持的情况下抢先实现。

按数据真实性收紧优先级：先把"已经在飞的路径"用真实数据喂满（第一期），再把"触发机制"和"数据结构"改造成通用的（第二期），最后再谈"任意地点在线取数"和自由相机（第三期）——每一期都可以独立验证，不需要一次性押注一个未经验证的大重构。
