# NASA SVS 14959「Moon 3D Models for Web, AR, and Animation」精度考证

页面：https://svs.gsfc.nasa.gov/14959/ （2026-01-29 发布）。Credits：Producer Dan Gallagher (eMITS)；**Data provider Ernie Wright (USRA)**——与本项目已用的 CGI Moon Kit（SVS 4720）同一位数据负责人，确认两者同源；Data analysts Tuomas Kankola、Josh Klint（Leadwerks Game Engine，说明网格经过游戏引擎向的精简/工具链处理，不是原始科学网格）。

## 方法

不下载整份文件（8k_Topo.glb 299MB、23k_Topo.usdz 302MB）做全量解析，而是：

- **GLB**：glTF 二进制容器结构是「12 字节头 + JSON chunk（含全部 accessor/mesh/材质/图像元数据）+ BIN chunk（顶点/索引/图像原始字节）」。用 HTTP Range 只取 JSON chunk（通常几 KB）即可拿到顶点数、三角形数、属性列表、图像尺寸引用；再用 Range 精确定位到 POSITION/INDICES 在 BIN chunk 中的字节区间，按需拉取（例如整段 POSITION 缓冲约 93MB，可视为"最贵的一次性成本"，其余都是几十到几百字节的探测请求）。
- **USDZ**：本质是 ZIP（要求内部条目不压缩，即 STORED），ZIP 的中央目录在文件尾部，用 Range 只取文件尾部几十 KB 即可拿到内部文件列表、每个条目的大小与偏移，再对小体积条目（如 PNG 贴图）做精确的字节级探测。
- **真实性交叉验证**：本机已缓存 NASA 官方 64 像素/度 LOLA 高程栅格 `/home/ubuntu/lunar-fm-assets/raw/ldem_64_uint.tif`（上一轮任务下载，真实测量数据，非本次新造）。用它反算模型网格顶点的真实地理位置与真实高程，核对模型的顶点位移是否确实来自真实地形，而不是凭空生成。
- 网格顶点间距通过在**真实 3D 空间**中做最近邻查询（`scipy.spatial.cKDTree`，对全部 812.6 万顶点建树，随机抽样 3000–8000 个查询点）得到，不依赖对经纬网格拓扑的假设——这样即使网格不是规则等距经纬格（后面会看到确实不是），间距数字依然可信。

## `Moon_NASA_LRO_8k_Topo.glb`（299 MB，贴图+地形）——精确结果

| 项目 | 数值 | 来源 |
| --- | --- | --- |
| 顶点数 | 8,126,284 | glTF accessor `count`（POSITION），精确值 |
| 三角形数 | 4,063,232 | INDICES accessor count / 3，精确值 |
| 顶点属性 | POSITION + **NORMAL**（内嵌，float32，逐顶点平滑法线）+ TEXCOORD_0 | 精确值，**法线确实内嵌**，不是运行时算的，也不是法线贴图（材质里只有 baseColorTexture，没有 normalTexture） |
| 彩色贴图 | 8192×4096 JPEG，约 4.63 MB | 从 BIN chunk 中该图像字节区间读取真实 JPEG 头，精确值 |
| 顶点间距（真实世界，3D 最近邻） | 中位数约 **3,870 m**，均值约 3,550 m（p10≈1,251 m 多在极区附近，p90≈5,289 m 多在中低纬） | 对真实顶点坐标做 KD-tree 最近邻查询后按 R=1,737,400 m 换算 |
| 网格拓扑 | **不是规则等距经纬格**：三角形顶点索引差值分散在 58–66、3–5 等多个值域，说明是纬度自适应密度的 UV 球（不同纬度环用不同列数，减少极区过密），而不是固定 W×H 网格 | 对索引缓冲（4,063,232 个三角形）做差值统计得出 |
| 极区处理 | 官方原文明确写「pinched poles are an artifact」；本项目对极区附近顶点的最近邻距离显著小于中低纬，证实极点确实是"许多顶点挤在一起收敛成一点"的贴图球典型瑕疵，不是真实地形 | 官方文字 + 实测最近邻距离分布 |
| 顶点位移幅度 vs 真实高程 | 模型半径范围（归一化单位）2.13%（(0.9781−0.9576)/0.9642）；同一坐标下 `ldem_64_uint.tif` 的真实全月起伏范围为 **19,871.5 m**（−9114.5 m 到 +10,757 m），占半径 1.14%；两者相除 ≈ **1.86 倍**——即**该模型的地形位移在几何上放大了约 1.9 倍**，不是逐点 1:1 真实高程 | 对 812.6 万顶点求半径 min/max/mean，与本机真实 LOLA 栅格独立算出的全月起伏范围对比 |
| 与真实地形的相关性 | 对模型顶点半径与其（推算）地理坐标处的真实 LOLA 高程做散点相关，在多组坐标系/朝向假设下搜索最佳对齐，最高相关系数约 **0.47**（正相关，非 1:1 高精度重建，说明网格顶点位移是对真实 LOLA 数据的**低通/平滑版本**叠加约 1.9 倍夸张，不是逐像素还原真实高频地形），但幅度夸张比例（1.86 倍）与已知真实起伏范围高度吻合，且该模型页面明确注明数据来自 LRO/Ernie Wright（与本项目现有 4720 数据同源）——**这是真实测量数据的可视化再加工，不是程序化生成的假地形**，但也不是可以直接拿来做科学定量分析的原始高程 |

## `Moon_NASA_LRO_23k_Topo.usdz`（302 MB，贴图+地形）——部分结果

USD 的二进制「Crate」格式（`.usdc`）是 Pixar 私有二进制格式，标准做法需要 USD SDK（`usd-core` 等）解析；本机 pip 镜像（`mirrors.tencentyun.com`）没有该包，无法在合理时间内安装，因此**网格顶点/三角形数无法精确获得**，如实标注为限制，不做没有把握的编造。已经拿到的确定信息：

- ZIP 结构：内部只有 2 个条目，`Moon_NASA_LRO_23k_Topo.usdc`（287,841,142 字节，未压缩存储）+ `Sphere_diffuse.png`（29,344,312 字节）。
- **贴图实测尺寸：4096×4096（正方形），8 位、RGB**——直接读取 PNG IHDR 头得到的精确值。这与「23k」命名直觉不符：并非 23000 像素宽的等距柱状图，而是一张 4096 见方的贴图。合理推断（非实测）：USDZ 面向 Apple AR Quick Look/RealityKit 交付，这类移动端 AR 管线历史上对贴图边长有 4096 上限的常见限制，"23k" 更可能标示的是**上游素材世代**（与 CGI Moon Kit 27k/23k 全球图的血缘关系），而不是这个 USDZ 文件里贴图的实际分辨率。
- `.usdc` 网格体积（287.8 MB，未压缩）与同一顶点布局假设下 8k_Topo.glb 的顶点+法线+UV 原始数据体积（260.0 MB）量级相当，但 USD Crate 格式本身支持数组级压缩，体积不能直接换算成顶点数，因此只能说**顶点规模很可能是几百万量级、与 8k GLB 同一数量级**，给不出精确数字。

## 贴图溯源：与本项目现有 8k 彩色贴图的关系

把 `8k_Topo.glb` 内嵌 JPEG 解码后与本项目 `src/assets/lroc-color-8k.webp`（上一轮任务从 CGI Moon Kit 4720 的 `lroc_color_poles_8k.tif` 派生）做像素级比对：

- 两者尺寸都是 8192×4096。
- 转灰度后做结构相关性（去均值/去方差后的归一化互相关）：**0.926**——高度相关，确认是**同一片真实月表影像**（陨石坑、月海边界完全对应同一地理位置）。
- 直接色彩逐像素差异较大（93.5% 像素差值 >10/255）——说明两者是**同一底图数据的不同色彩处理版本**（这个 14959 模型的贴图做了更"电影感"的对比度/曝光再加工，不是 CGI Moon Kit 那版 Hapke 归一化反照率），不能直接替换使用，但确认了"同源"判断成立。

## 核心结论：直接问题作答

**问：如果直接 zoom 到月表，这个模型大概什么精度？离"1 米/像素"差几个量级？**

以 `8k_Topo.glb`（当前可精确测量、且比 23k USDZ 更适合直接在 three.js 里用的版本）为准，在赤道换算：

- **贴图地面分辨率**：8192 像素环绕 2π×1,737,400 m 周长，赤道处约 **1,333 m/像素**。相对 1 m/px，差 **约 1,333 倍，10^3.12（约 3.1 个数量级）**。
- **几何网格分辨率（真实位移能分辨的最小起伏尺度）**：真实顶点间距中位数约 **3,870 m**。相对 1 m/px，差 **约 3,870 倍，10^3.59（约 3.6 个数量级）**；而且这套位移还叠加了约 1.86 倍的垂直夸张，不是科学定量数据。
- 换句话说：**这是一个"整月轨道俯瞰"级别的资产，分辨率比 1 米/像素粗了 3–3.6 个数量级（千倍到近万倍），完全不足以支撑"贴地漫游"体验**——不管是贴图细节还是几何起伏，尺度都停留在"能看清月海和大型高地地形起伏"，看不到单个陨石坑内部结构，更看不到岩石。23k USDZ 因为暴露出的贴图实测只有 4096×4096（更粗，约 2,665 m/px），геометрия 未知但量级相仿，结论一致甚至更保守。

**问：跟我们现在站里已有的 0.6 米/像素 NAC 走廊数据是什么关系？谁粗谁细？能不能互补？**

- 我们现有 Taurus–Littrow NAC 走廊：0.6 m/px 影像、2 m 高程网格间距——比 14959 模型的网格间距（约 3,870 m）精细 **约 6,449 倍**，比它的贴图（1,333 m/px）精细 **约 2,222 倍**。NAC 数据精细得多，不是一个量级。
- 关系是**严格互补，不是竞争**：14959 模型（或其上游 4720 的 64 ppd 高程、27k/16k/8k 彩色图）适合覆盖"整月轨道到远景"这一档；NAC 数据只能覆盖"已经人工处理过配准的具体走廊"这一档；中间还缺一档"区域级"（比如 WAC 100 m/GLD100，本项目已经在用于 Taurus–Littrow 外圈过渡）。三者天然构成一个 LOD 阶梯：**全球（~1–3 km/px）→ 区域（~100 m/px）→ 局部测量走廊（~0.6–2 m/px）**，这正是第二部分方案要落地的分级结构。
- 直接结论：**这个 14959 模型不能替代或提升我们现有的 NAC 走廊精度**，它的价值在于给"全球最低档"提供一个官方现成、经过验证的参考基准（我们上一轮已经自己从 4720 的 64 ppd 原始栅格做到了同量级甚至更贴近科学数据的全球高程+法线贴图，没有 1.86 倍夸张，是本项目目前更优的全球层来源），但它确认了"整月轨道级"精度的行业惯例数量级，可以作为我们全球 LOD 最外层的精度基准和交叉验证对象。

## 对工程决策的启示（承接第二部分方案）

1. 不建议直接把 14959 的 GLB/USDZ 网格整体导入项目：（a）8.1M 顶点/4M 三角形对于一个"最外层、离得最远"的 LOD 层来说过重；（b）1.86 倍垂直夸张不适合与我们其余各档（无夸张）的真实数据混用，混用会在 LOD 切换时出现"同一撞击坑，远看更深、近看变浅"的不连续感；（c）法线是逐顶点烘焙在这批特定顶点上的，不能独立于这份网格复用。
2. 但它的**思路**——"贴图分辨率与网格密度分两个维度分级供不同距离使用"——直接验证了 LOD 引擎方案的合理性，且它的 Small/Full 分级体积比（77.7MB/298.9MB≈26%，顶点数比 2,021,340/8,126,284≈24.9%，接近线性）可以作为我们自己设计分级粒度时的参考数量级。
3. 我们已有的全球层（8k 彩色 + 64 ppd 真实高程重算的法线贴图，无夸张）在"贴图分辨率"和"数据真实性"两项上都不弱于甚至优于 14959 模型，缺的是**真正的多档动态几何 LOD**（我们目前全局网格是固定约 30 km 顶点间距的粗网格，只有法线贴图在做视觉补偿，没有真实几何起伏可供近距离察觉）——这是第二部分方案要补的核心缺口。
